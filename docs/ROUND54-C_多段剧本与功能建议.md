### 1.2 方案决策评审（7 个关键问题）

| # | 决策点 | 选项 | 评审结论（建议） |
|---|---|---|---|
| 1 | **输入形态** | (a) 分隔符整段文本；(b) JSON 章节数组；(c) 章节文件列表/目录；(d) 节点连多个 STRING | **MVP=(a) 已实现**；**完整版建议 (b)+(c)** 并存：`多段剧本` 保持文本，另加 `剧本文件列表`（每行一个 .txt/.md 路径，按顺序）与「目录模式」（按文件名排序）。分隔符规则要写进 tooltip：仅整行匹配、支持自定义（`---`/`===`/`第N章` 需明确"仅整行"语义，避免正文误切）。**不要**把章节塞进一次 API（违背"避免长上下文漂移"的初衷）。 |
| 2 | **每章 API 次数** | 每章 1 次 vs 合并 1 次 | **每章 1 次**（当前实现）是**正确**的：每章独立上下文=避免漂移，且失败只影响一章。代价：N 章=N 次 API；应在节点显示「预计 API 次数=章数」并在审计累计。**可选增强**：章间加「前情摘要」（上一章末 ~200 字或 AI 摘要）作为下一章 user prompt 前缀，否则章节剧情可能不连贯（素材一致≠剧情连续）。 |
| 3 | **素材库跨章复用** | 同项目复用 / 复制到新项目 / 每章独立 | **同项目复用（当前）正确**（用户诉求：人物不漂移）。但要补三条：①章间「名称漂移」用 fallback_pick 补足时，必须审计标明「名称未匹配→项目库补足」；②补足参考应**按角色/场景/物品槽位**而非只按优先级截断（见 §2）；③若用户切换项目跑同一剧本，参考图会串库（无冲突检测）→ 建议 `项目` 参数变化时告警。 |
| 4 | **22 帧跨章语义** | 章内连续 / 章间 pin / 章间近似 | **现状=章内连续+章间硬切**（`one_stop:2016-2017`）。评审：**章间做"真 pin"目前不可行**（每章是独立 `_run_single`→独立 `execute`，vendor 的 pin 依赖同一 execute 内上一段 AV latent/缓存；跨 execute 拿不到）。**建议完整版=章间"上一章尾帧作下一章首段参考图"近似**（与长片跨批同一策略，`one_stop:1755-1766`，已在批次间实现），并在 report 标 `cross_chapter_mode="last_frame_ref"`；**绝不要把近似写成"原生 22 帧 pin"**（诚实边界，见 `director_longform.py:7-11`）。可选：章间加 0.3–0.5s 淡入淡出掩盖硬切。 |
| 5 | **每章输出 vs 总片** | 只总片 / 只分章 / 两者+清单 | **现状=每章 mp4 + 总片 mp4 + report`multi_script`**，正确。**缺口**：总片没有「章节清单/manifest」（章 id、时长、段数、API 次数、审核分数、是否缺章），也没有总片级审核；建议补 `multi_script.chapters[]` 已有雏形（`one_stop:2012-2014`）→ 增加 `duration/segments/verdict/缺章标记`，并写入最终元数据（OUT3）。 |
| 6 | **失败/中断/断点续跑** | 章级续跑 / 全部重跑 | **现状=MVP：失败章继续+最后拼接成功章；无章级检查点**。问题：①中断后重跑从第 1 章开始（每章内容不同→长片批次指纹不同→章内检查点也难命中）；②缺章直接拼接会产出「少一章却显示成功」的成片（假成功风险，虽然 summary 有记录）。**完整版建议**：`_work/multi_script.json` 章级检查点（`{chapter_index, script_sha256, final_path, ok, elapsed, api_calls}`，用项目+参数+章内容 hash 做指纹），重跑跳过已完成且文件存在的章；缺章策略参数 `缺章策略 = 阻止输出 / 降级输出(记录) / 继续拼接`。 |
| 7 | **命名与项目冲突** | 固定名 / 版本化 | **现状**：章节名 `{stem}_第NN章{suffix}`（`one_stop:1961`），工整但**重跑会覆盖同名文件**（项目 output 与 ComfyUI output 均可能覆盖/加序号）；项目固定为同一 `项目`，同项目重跑=素材累积（预期），但**章名固定→历史版本不可追溯**。建议：章节文件名加 `_run{ts}` 或版本 `vN`；report 记录章 hash；同名检测时显式告警。 |

### 1.3 MVP vs 完整版差异表

| 能力 | MVP（当前已实现/建议立即补） | 完整版 |
|---|---|---|

| 执行 | 逐章 `_run_single`，同项目；失败章继续 | 章级共享模型上下文（避免每章重复 load H3）；可选中止/暂停 |
| 素材 | 同项目 LOCKED 复用 + 项目库补足（≤9，超 9 告警） | 角色/场景/物品槽位绑定；模板化参考优先级；跨项目冲突检测 |

### 1.5 与现有机制的交互/冲突（逐项）

| 现有机制 | 交互 | 风险/建议 |
|---|---|---|
| `_run_single` 全流程 | 每章完整跑一遍（提示词→素材→审核→出片→Finalize→审核） | 正确但重；**每章会重新 load/unload H3 模型**（`_load_video_models`/`_free_models`）→ 建议多段模式共享模型上下文（或至少 `批次间卸载模型` 语义扩展到章间） |
| 长片分批（章内） | 章内仍按 `每批段数` 分批 + 检查点 | 章内检查点指纹含 prompts/段数等；**章间内容不同，章内检查点天然隔离**，但多段模式没有章级索引 → 重跑从第 1 章开始 |
| 自动返工/级联（CNT2/CNT3） | 每章内部独立返工 | 正确；但**总片级不汇总 CNT2/CNT3**，且缺章/降级不进总片元数据 → 建议总片 manifest 汇总 |
| 视频审核 R_seg/R_full | 每章 `_run_single` 末尾各跑一次 R_full | **每章一次 R_full ≠ 总片一次 R_full**：SG6 要求「最终整片审核在 S_OUT 之前执行一次」→ 建议总片拼接后再跑一次 R_full（或明确参数 `章级审核/总片审核`） |
| 22 帧连续性 | 章内原生 pin；章间硬切 | 见 §1.2-4；建议章间 last-frame 参考近似 + 转场，报告如实标注 |
| 项目隔离/素材累积 | 同项目累积（预期）；换项目会读另一个库 | 建议多段模式启动时打印项目 id/素材数，防误选 |
| 素材审核人工等待 | 每章可能长时间等待人工 | 多段模式如果开「人工审核」会串行阻塞 N 次；建议多段模式强制/建议模型审核，或提供「全部章等待」队列视图（UI 缺口） |
| Finalize/剪辑 | 每章 Finalize 一次 + 总片再 splice | 总片 splice 用 `director_edit.splice_segments`（默认无转场），与单章 Finalize 的编码参数可能不一致 → 建议总片统一走 `pipeline.encode` 或 `finish_movie`（`director_edit.py:387`） |

## 2. 素材数量上限策略（生成数量 vs 挂参考图分离）

### 2.1 三处上限的现状（实测）

### 2.2 冲突分析

1. **三个概念被混在一个参数里**：「生成多少张（候选/库容量）」≠「每类库上限」≠「每段挂多少参考图」。用户说"尽量到模型极限"，指的应是**生成/入库**尽量多；但**挂参考图**受 vendor 硬上限 9 约束，无法突破（突破=改 vendor/schema，不建议）。
2. **当前已做的正确设计**（值得保留并明确写进文档）：生成并 LOCK 可到 64，**只挂前 9 张**，其余不丢（仍在库中、可人工替换/后续章复用）；超限有审计告警（`one_stop:577` tooltip、`:1929-1932`、`everything_node:646-649`）。
3. **风险点**：
   - **截断顺序**：当前 Everything 按 `_ASSET_PRIORITY` 排序（角色>场景>物品>分镜，`everything_node.py:595`）后取前 9；单节点补足按 `store.list_assets()` 顺序（`one_stop:1905`/`:2288`）→ **两处优先级不一致**，可能把角色挤掉。
   - **per_class_limit 与 total 的交互**：生成 64 张但每类上限 9 → 实际每类最多 9 条（版本可多）；若用户要「同一角色多候选 12 张」会被 per_class_limit 拦（除非是同一 asset 的多版本）。需明确：per_class_limit 限制的是**条目数**还是**版本数**（`ROUND50-A:113` 判「超限拒绝」）。
   - **64 的代价**：每张 SDXL 2–6s（4090 实测 12.36s/张 于 S3 链路，`ROUND37:266`）→ 64 张≈13 分钟+；显存/磁盘/审核轮次（每张最多 3 轮 CNT1）线性增长。默认不宜 64。
   - **一致性评分参考**：素材审核「一致性=与同素材上一 LOCK 版本直方图/边缘相关」（ROUND53），多候选多版本会提高 LOCK 概率但也可能把"同质化候选"当一致。
