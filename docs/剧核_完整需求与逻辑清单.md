### 1.3 全局硬语义（改代码前必须背下来）

来源：`docs/项目深度理解_接手基线.md:95-113`；docx 第七部分（提取 `:380-723`）；`docs/CONTRACTS.md:45-53`。

1. **五条契约硬规则 R1–R5**（`docs/CONTRACTS.md:45-53`）：
   R1 存在性只能程序判断；R2 素材库只追加不覆盖；R3 LOCK 绑 `asset_id+version+content_hash`；
   R4 CNT1/2/3 语义隔离、技术失败不消耗；R5 项目隔离（路径必须含 project_id）。
2. **审核对象 = 素材条目 + 具体版本**；每版本独立指纹/审核记录/最终结论（docx 提取 `:383`）。
3. **LOCK = `LOCK_{素材全局ID}_{版本号}`**，只授权对应版本；来源三值 `HUMAN_PASS/MODEL_PASS/FALLBACK_PASS`；新版本绝不继承（docx 提取 `:390`、`:424`）。
4. **FALLBACK 不伪装成普通通过**（docx 提取 `:388`、`:400`）。
5. **CNT1=素材模型审核候选轮次**（人工不计、切模型从 0、版本递增不清零，默认≤3，docx 提取 `:386`）。
6. **CNT2=当前问题段质量返工**；**CNT3=级联段重生成**；两者独立、不互相加、不因版本递增清零（docx 提取 `:398-399`）。
7. **技术失败 FAILED ≠ 质量不合格 BLOCKED**；FAILED 不占候选/重做次数（docx 提取 `:534-536`、`:639`；`docs/CONTRACTS.md:52`）。
8. **H_arb 唯一提交**：人工/模型并发迟到结果按同一后端时间戳仲裁，人工更早→人工胜+ABORT_SIGNAL；否则模型胜且人工只记日志；最终结论只提交一次（`docs/CONTRACTS.md:381-399`；docx 提取 `:391-392`、`:656-659`）。
9. **R_seg 与 R_full 维度不同**；`R_full` 只在最终拼接后、S_OUT 前执行一次（dot `:177`；docx 提取 `:397`）。
10. **级联必须终止**：只有依赖确实失效才继续标记；`max_cascade_depth` 生效（`docs/CONTRACTS.md:466-469`）。
11. **整片失败策略必须显式**：`BLOCK_OUTPUT` 或 `DEGRADE_OUTPUT`（记录 FULL_REVIEW_DEGRADED），未配置必须报错（`docs/CONTRACTS.md:508-511`、`:549-551`）。
12. **标识体系**：12 个审核状态码、22 条状态转移、ID 不含可变状态、原子写（tmp+`os.replace`）、文件锁贯穿 read-modify-write、幂等键 canonical_json→SHA-256、内容指纹 `sha256:{hex}`（docx 第七部分 `:406-708`；`docs/CONTRACTS.md:94-121`）。
13. **mock 与真实必须可区分且落盘**：`MovieMetadata.generation_provenance` 必填（is_mock/executor/reason/unverified），空即拒写（`docs/CONTRACTS.md:620-627`；`docs/第一阶段总交付与总检查报告.md:77-78`）。

**审核状态码 12 个**（docx 第七部分·五，提取 `:493-540`）：
`RECEIVED / VALIDATING / SCANNING / CLASSIFYING / AWAITING_REVIEW / TIMEOUT / ARBITRATING /
ALLOWED / BLOCKED / FALLBACK / FAILED / ABORTED`，每个状态有唯一目标状态（状态转移表 22 条，提取 `:542-639`）。

**关键语义澄清（CONTRACTS v1.2 裁定，`docs/CONTRACTS.md:326-345`）**：
- `AWAITING_REVIEW` 是**初始状态**（转移表中无 target=AWAITING_REVIEW 的边），人工周期**不经过 SCANNING/CLASSIFYING**；
  人工模式下确定性校验失败走 `RECEIVED→VALIDATING→FAILED`。
- `FALLBACK` 时 `ReviewRecord.version` = **被选中的最高分候选版本**（LOCK 授权的那个），content_hash 必须一致。
- `FAILED→RECEIVED`（技术恢复/重新提交）是方案明确列出的**允许例外**；终态约束是「终态不得有质量重试出边」。

**FAILED ≠ BLOCKED**（本题重点）：
- `BLOCKED`=审核未通过、等待优化/新候选，**属于质量候选流程**（docx 提取 `:526-528`）；
- `FAILED`=技术失败，保存错误原因，按技术重试/恢复处理，**不计为质量不合格候选**（docx 提取 `:534-536`）；
- 状态转移表：`SCANNING 技术失败→FAILED`（"技术失败不占用内容候选上限"，提取 `:563-566`）；
- 契约层：`ErrorClass != QUALITY_REVIEW` 的技术失败绝不消耗 CNT2/CNT3（`docs/CONTRACTS.md:52`）；
  `_tech` 计数 key 为 `CNT_{obj_id}_TECH`，与 CNT1/2/3 完全分离（`docs/CONTRACTS.md:602`）。

## 3. 段间连续性：准确语义（「前 22 帧 ~ 后 22 帧保持首尾一致关联」）

### 3.1 需求原文（三处，逐字）

1. **愿景**：「导演节点自动取前段尾部 22 帧做参考或前一帧衔接，不需要手动切换，参考模式均可，节点自动处理。」
   ——`文档/愿景部分_纯文本.txt:33`；docx 提取 `:36`
2. **原则**：「连贯性主来源不能是前一帧，必须是素材库参考图。……尾部 22 帧只作动作、镜头、光线、节奏的辅助连续。
   人物不在最后几帧时，必须由素材库角色图锁定身份，禁止仅用前一帧替代素材库参考。」
   ——`文档/愿景部分_纯文本.txt:35`；docx 提取 `:38`
3. **用户纠正（最直接）**：「并没有说不让前一帧。**那个导演节点里就支持前 22 帧给下一个，音频等也会给下一个，
   可以勾选，保持画风、音频一致，而且那个节点默认就支持**。只是我要再用一个素材库，防止人物不在那个区间内。」
   ——`docs/需求与意见汇总.md:90`；追补：「**最后 22 帧只是保风格的**，因为那个插点就支持原生的……
   素材库完整地提交给下一段视频，所有素材都提交给下一段视频」——`:91`。

### 3.2 准确语义（把「前 22 帧 ~ 后 22 帧」说清楚）

**一句话**：上一段的**尾部 22 帧（含音频尾部）被钉进下一段的开头 22 帧位置**作为"运动上下文"
（Motion Context，永不参与去噪的条件注入，不是普通参考图）；生成后把这段前缀裁掉只输出新画面。
于是下一段的**前 22 帧画面/音频 = 上一段的后 22 帧**，剪在一起时接缝"首尾一致"、画风/动作/音频连续。
这是导演台**原生**能力（可勾选开关），与素材库参考图**叠加**使用，不是二选一：

- **素材库参考图** = 身份/造型/场景/物品一致性（主来源，R3：只挂已 LOCK 版本）；
- **尾部 22 帧** = 动作/镜头/光线/节奏/音频辅助连续（辅助，导演台原生）。

**准确参数（vendor 源码实证）**：

| 参数/机制 | 值/行为 | 源码位置 |
